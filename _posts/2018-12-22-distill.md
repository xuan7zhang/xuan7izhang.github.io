## Bug Summary

把原本在 4x L40S/CUDA 上运行的 OPSD OGLS-SD 训练脚本迁移到 AWS Trn2/Trainium2 后，问题的根源不是单个参数错位，而是 CUDA 训练栈（CUDA/NCCL/DeepSpeed/FlashAttention + Transformers 的 GPU 采样实现）与 Neuron/XLA 编译栈之间的不兼容。

原脚本假定一套在 GPU 上可用且可编译的算子（例如全词表排序、`torch.isin`、top-p sampling、NCCL 通信等）。在 Trn2 上，这些要么不可用、要么会触发 Neuron 编译器产生不被支持的 HLO op，从而导致编译失败或运行时错误。

## 主要症状

1. 环境问题：系统默认 `python3` 为 3.9，但 `accelerate==1.11.0` 要求 Python 3.10+

  解决：使用 `/usr/bin/python3.11` 重建虚拟环境并安装 Trn2 专用依赖：`requirements_trn2.txt`。

2. Accelerate XLA launcher 报错：

```
Your training script should have a function named main
```

  解决：将 `opsd_train.py` 从直接在模块顶层执行改成 `def main(): ...`，并在文件末尾调用 `main()`；这样 XLA launcher 能找到入口。 

3. WandB 在 XLA 子进程中 no-tty：

```
api_key not configured (no-tty)
```

  解决：在线运行时显式导出 API key：

```bash
export WANDB_API_KEY=... 
WANDB_MODE=online bash scripts/run_opsd_l40s_4gpu_ogls_sd.sh
```

  或者在代码中检测无 key 的情况自动 fallback 为 offline 模式。

4. Neuron 编译器报 `int64 dot`：

```
Opcode (dot) does not support 64-bit integer operands
```

  解决：临时通过 `neuronx-cc` flags 绕过严格的 HLO 操作数类型检查：

```bash
NEURON_CC_FLAGS="--disable-hlo-operand-type-check evrf_035"
```

5. 最大的坑：Transformers 的 `generate()` 在 Trn2 上触发不被支持的 `sort` 操作：

```
Operation sort is not supported on trn2
%sort = ... sort(... vocab_size ...)
```

  一开始怀疑是 EOS stopping criteria 中的 `torch.isin`，随后又发现 top-p / sampling 的路径也会触发对全词表的排序。经过多次尝试，继续修补 `generate()` 不是稳定方案，最终选择在 Neuron 环境下完全绕过 `model.generate()`，改用更小且可编译的生成路径。

## 最终解决方案（核心）

在 Neuron/Trn2 上不使用 Transformers 的 `model.generate()`，改用自定义的 greedy decode（仅使用 `argmax`，避免排序、top-p、采样等）：

```python
for _ in range(max_new_tokens):
   outputs = model(
      input_ids=next_input_ids,
      attention_mask=current_attention_mask,
      past_key_values=past_key_values,
      use_cache=True,
      return_dict=True,
   )
   next_token = outputs.logits[:, -1, :].argmax(dim=-1, keepdim=True)
   generated = torch.cat([generated, next_token], dim=1)
   current_attention_mask = torch.cat(
      [current_attention_mask, torch.ones_like(next_token)], dim=1
   )
   next_input_ids = next_token
   past_key_values = outputs.past_key_values
```

通过环境变量控制行为：

```bash
export PJRT_DEVICE=NEURON
export OPSD_NEURON_CUSTOM_GREEDY=1
export OPSD_GENERATION_DO_SAMPLE=0
export TOP_P=1.0
```

在该模式下，生成阶段只走最小可编译路径（greedy + argmax），避免触发 Neuron 编译器不支持的 HLO。

## Takeaway（迁移经验）

Trn2/Trainium 的迁移不是把 CUDA 改成 Neuron 就完成。训练的前向/反向（forward/backward）路径虽然多数情况下能通过编译，但在 on-policy RL、self-distillation 或任何在训练中调用模型生成（`generate()`）的任务里，生成逻辑里常见的 GPU 优化（如全词表排序、top-p、sampling warper、`torch.isin`）极易踩到 XLA/Neuron 的编译限制。

稳妥的迁移策略：

```
先用最小可编译的 generation path 跑通（greedy + argmax + no top-p + no sampling），
再逐步恢复复杂采样功能并验证每一步是否可编译。
```

## 项目侧实际改动（摘要）

- 新增 `accelerate_trn2_ogls.yaml`
- 新增 `requirements_trn2.txt`
- launcher 改为通过 Neuron/XLA 的环境变量启动
- 将 `opsd_train.py` 改为包含 `main()` 并在 Neuron 下默认使用 `sdpa`
- `opsd_trainer.py` 在 Neuron 下绕开 `transformers.generate()`，使用自定义 greedy decode
- WandB 支持 online/offline 的显式控制（环境变量控制）
